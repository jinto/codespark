Decision Snapshot

지금 무엇을 정하고 무엇을 열어두는지에 대한 스냅샷입니다. 선택은 아래 카드에서 바꿀 수 있고 맨 아래 generator가 그대로 텍스트로 묶어 줍니다.

범위 경계: 이번 문서는 worktree를 어떻게 보여줄지에 대한 UI 계층·탭바 스코프·도달 불가 기능 정리까지입니다. git worktree 생성/삭제 로직 자체의 재설계, 원격(SSH) worktree 지원, 브랜치 관리 기능 확장은 범위 밖입니다.
  • 이미 고정된 것: 워크스페이스 = 워크트리 1:1 매핑 규칙, 세션의 워크스페이스 소속을 생성 시점에 고정하는 sessions.workspace_path(오늘 도입), flat worktree 명명 <repo>-<branch>-<id>.
  • 핵심 오픈 항목: 표시 계층(사이드바 트리 / 스트립 / 탭바 그룹), 탭바가 활성 워크트리만 보여줄지, 좁은 사이드바(최대 180pt)를 어떻게 감당할지.
  • 드러난 결함: model.workspaces는 계산만 되고 렌더링되지 않으며, removeWorktree는 UI 호출자가 없어 앱에서 워크트리를 지울 수 없습니다. 워크트리로 연 탭 제목은 전부 Terminal이라 구분이 불가능합니다.
  • 구현 전에 정해야 하는 이유: Q-01(표시 계층)과 Q-02(탭바 스코프)가 나머지 13개 카드의 전제입니다. 이 둘이 흔들리면 사이드바·탭바·단축키·저장 스키마가 연쇄로 재작업됩니다.
Smallest safe slice: Q-01에서 고른 표시 계층 + Q-07 탭 제목(브랜치명)만 먼저 낸다. 이 조합은 읽기 전용 변경이라 저장 스키마·git 조작을 건드리지 않고, 되돌리기 비용이 거의 0입니다.
NO-GO 경계: 같은 슬라이스에서 (1) 탭바 스코프 변경, (2) workspace_path 저장 스키마 변경, (3) 워크트리 삭제/입양 같은 파괴적 git 조작을 함께 넣지 않습니다. 특히 git worktree remove를 UI에 노출하는 작업은 되돌릴 수 없는 파일 삭제를 동반하므로 별도 슬라이스에서 확인 대화상자와 함께 다룹니다.

Decision Questions

15개 카드입니다. Q-01과 Q-02가 상위 결정이고 나머지는 그에 종속되거나 독립적으로 정리 가능한 항목입니다.

Q-01 worktree 표시 계층 상위 결정

사용자 요청: "orca를 써보니 하나의 repo 아래에 여러 개의 worktree들이 보이는 게 관리가 더 편해 보였다." — 그 구조를 CodeSpark의 어느 계층에 넣을지 정합니다.

근거: 사이드바는 프로젝트 평면 목록, 탭바는 전체 세션 평면 목록이고 워크스페이스는 렌더링되지 않습니다. 반면 모델에는 워크스페이스별 선택 기억·전환 시맨틱이 이미 있습니다. SidebarView.swift:72 / MainContentView.swift:16 / AppModel.swift:34-49
A안 — 사이드바 트리 B안 — 워크트리 스트립 ▾ codespark ┌ codespark ───────────────┐ main 1 │ [main 1] [feat-auth 2] + │ feat-auth a3f1 2 │ Terminal × Terminal │ emac └──────────────────────────┘ ▸ goodgirl
Q-02 탭바 스코프 — 활성 워크트리만 vs 전체 상위 결정

"관리가 편하다"의 실체가 여기서 갈립니다. 워크트리를 고르면 탭바가 그 워크트리 것만 보여줄지, 아니면 전체를 계속 보여줄지.

근거: 현재 탭바는 model.liveSessions(프로젝트 전체)를 받습니다. 반면 workspaceSelectedSessions는 워크스페이스별로 마지막 선택 탭을 기억하도록 설계돼 있어, 필터링을 전제한 구조입니다. MainContentView.swift:16 / AppModel.swift:49
Q-03 사이드바 폭 처리 (Q-01 = A일 때)

트리를 고르면 즉시 물리적 제약에 부딪힙니다. 들여쓰기 + 브랜치명 + 카운트가 현재 최대 폭에 들어가지 않습니다.

근거: .navigationSplitViewColumnWidth(min: 100, ideal: 120, max: 180) — 최대 180pt. 프로젝트 행은 이미 이름 + 정보줄 2줄 구조입니다. CodeSparkApp.swift:43 / SidebarView.swift:28-35
Q-04 사이드바를 숨겼을 때의 워크트리 전환 수단

사이드바는 Cmd+Ctrl+S로 토글되고 프로젝트가 없으면 자동으로 숨습니다. 트리에만 의존하면 숨긴 상태에서 워크트리를 바꿀 방법이 사라집니다.

근거: 사이드바 가시성은 @AppStorage(StorageKeys.isSidebarVisible)로 영속화되며 토글 가능합니다. 한편 .navigationSubtitle은 이미 브랜치를 표시하고 있어 활성 워크트리 표시에 재사용할 수 있습니다. CodeSparkApp.swift:23, 49, 116-121
Q-05 접기 기본값과 inactive 축약 정책

ISSUES.md에 이미 상충하는 두 요구가 적혀 있습니다: "inactive ws들은 ... 같은 걸로 줄여서 한 줄에 표시하고 몇 개인지 숫자를 표시" 와 "active는 항상 펼쳐주세요. 안 그러면 Cmd 키를 눌러도 안 보여요."

근거: StorageKeys.expandedProjectIDs가 선언만 되고 쓰이지 않습니다. 접기 상태를 영속화할 자리는 이미 있지만 정책이 없습니다. StorageKeys.swift:6 / ISSUES.md / ISSUE01.md
Q-06 탭이 0개인 워크트리를 표시할 것인가

현재 groupSessions는 탭이 없는 워크트리도 빈 워크스페이스로 반환합니다. 이걸 UI에 그대로 노출할지 정해야 합니다.

근거: worktrees.map { ... sessions: buckets[wt.path] ?? [] } — 워크트리 목록을 그대로 매핑하므로 빈 워크트리도 항상 포함됩니다. ProjectViewData.swift:199-207
Q-07 탭 제목 기본값

현재 워크트리로 연 탭도 제목이 Terminal 고정이라, 탭바만 봐서는 어느 워크트리인지 알 수 없습니다.

근거: addWorktree가 newSession(inWorkspacePath:)를 호출하고, 거기서 제목이 "Terminal"로 하드코딩됩니다. AppModel.swift:506, 636-648
Q-08 사라진 워크트리에 속한 탭 처리

워크트리를 지우거나 경로가 바뀌면 그 탭들의 workspace_path가 아무 워크트리와도 매칭되지 않습니다. 현재는 조용히 메인 워크트리로 흡수됩니다.

파생 상태 위험: 소속이 경로로 저장되고 매칭도 경로 동일성입니다. 같은 브랜치로 워크트리를 재생성하면 id 4자리가 달라져 매칭이 깨집니다. 현재 폴백 동작은 테스트로 고정돼 있습니다. ProjectViewData.swift:186-196 / WorkspaceSelectionTests.swift:367
Q-09 워크트리 캐시 미스 시 구조 깜빡임

캐시가 비어 있으면 워크트리가 여러 개인 프로젝트도 합성 워크스페이스 1개로 접혔다가, 로드 후 여러 개로 갈라집니다. 트리 UI에서는 이 깜빡임이 눈에 띕니다.
